# 提交与 PR 持续检查

按用户 2026-10-23 的明确范围：**每次分支提交与每个 PR 检查源码和测试，不设每周扫描。**
此前维护设计中的周度扫描、定时 CodeQL、Dependabot 周期更新不实施。

## 触发与检查内容

| 流程 | 触发 | 内容 |
| --- | --- | --- |
| [Source and tests](../.github/workflows/checks.yml) | 所有分支 push、所有 PR、手动运行 | 锁定依赖、公开源码检查、前端三时区测试、源码归档/私密路径回归、前端构建、网关测试 |
| [Windows build and release](../.github/workflows/release-windows.yml) | main push、面向 main 的 PR、v 版本标签、手动运行 | 原生持久化、更新/安装准备、发布引用、浏览器交互/跨日/布局、正式构建与安装器保留验收 |

GitHub 不会观察尚未推送的本地 commit；检查在 push 或 PR 事件后运行。
带 `[skip ci]` 等跳过标记的提交可能不运行，不应在版本归档描述中使用。
没有 `schedule`、每周提醒、周期依赖 PR、自动合并或新增自动发布入口。

## 合并前检查

1. 打开 PR 的 Checks，核对准确提交 SHA 和相应检查状态，失败先分诊。
2. 数据相关变化必须有合成数据验证与备份/恢复证据，不能只看前端测试数量。
3. 检查新增依赖、权限、第三方许可和公开文件范围；不对审计未知项声称安全。
4. 说明剩余风险、兼容性及回退方式，再由维护者决定合并和发布。

公开源码检查覆盖当前已跟踪及未忽略源码中的明确私密路径和常见秘密模式，
**不是全历史秘密扫描，也不是依赖漏洞扫描**。需要时手动执行 npm/OSV/RustSec 审计，
日期、范围、工具失败与结果分别记录，不把网络失败当作零漏洞。

## 发布与数据保护

普通提交不应被旧发布标签拦截。真正发布仍验证版本和源码 SHA，拒绝覆盖已有版本。
main 的完整 Windows 流程不取代本机更新备份；真实安装更新仍遵循
[开发与安装规则](development.md#正式构建与安装)。

是否已推送、首次 GitHub 运行是否通过，以 [Actions](https://github.com/keykonor/focus-matrix/actions)
真实记录为准；配置与本地校验不等于远端运行通过。
工作流通过也不代表 main 已启用必需检查规则。传统分支保护读取此前返回权限不足，状态待管理员核验。

## 遗留项

[本轮技术审计](security/technical-review-20261023.md) 记录已修复问题。
[开源初审](security/open-source-audit-20261023.md) 中网站依赖漏洞、CSP、权限、未维护 Rust 依赖、
图标来源、组件许可和签名仍需分项处理；本轮没有宣称它们已修复。

严重漏洞或凭据泄漏先停用/撤销受影响凭据，再私下分诊与修复，不公开实际密钥或用户数据。
关闭问题需要修复提交、针对复现的回归结果和必要的发布/部署证据。
